## 1. Identity: derived from the ledger, not minted

    release_id = "rel-g1-" + SHA256_US("araripe.green.release/1",
        ledger_id, run_manifest_id, run_manifest_sha256, document_sha256)

No clock, no run id, no actor, no counter. The briefing asked for identity
derived "from what the ledger already seals … instead of inventing a second
axis of identity", and the consequence is stronger than it first looks:

1. the same ledger maps to the same prefix, so **republishing is a byte-exact
   no-op**, not a conflict;
2. any change to the ledger lands on a **different** prefix, so an existing
   release cannot be addressed with different content at all;
3. therefore even a conditional write that somehow failed to guard could only
   overwrite byte-identical content.

Point 3 is why `conditional_store` is a *second* line of defence rather than
the only one — and the gap it covers is precise: a `date_product` is computed
by the publisher, not sealed by the ledger, so the same ledger with a
different renderer gives the same prefix and different bytes. That case is the
one `If-None-Match: *` catches, and the test for it uses exactly that shape
rather than a synthetic checksum edit.

**The manifest deliberately carries no publication provenance.** Adding
`built_utc` or a run id would make its bytes non-reproducible and destroy
property 1, so those belong to the pointer, which describes a promotion
*event*. `test_the_manifest_carries_no_publication_provenance` holds the line.

The manifest is stored as canonical JSON. Requiring canonical *file* bytes is
legitimate here and was refused for the ledger, and the difference is
authorship: the ledger's bytes come from a producer whose example generator
pretty-prints, and these bytes come from this module. The stored `ledger.json`
is re-encoded canonically for the same reason — the producer's digests cover
the parsed structure and its runtime writer emits exactly these bytes — which
also keeps two differently formatted copies of one ledger from becoming two
different releases.

## 2. The zero-alert distinction, read out of the contract

`complete_zero_alerts` is a first-class terminal state, so the publication
layer must not guess. Rather than hardcode two status names,
`ledger_binding.pinned_status_semantics()` derives both properties from the
pinned schema's own per-status conditionals:

- `artifact_sealing` = statuses whose branch constrains
  `output.artifact_sha256` to a sha256 → `{complete_with_alerts,
  complete_zero_alerts}`;
- `alert_bearing` = statuses whose branch requires `observation_count >= 1` →
  `{complete_with_alerts}`.

So "usable" and "holds alerts" are statements about the contract, not about
magic strings. Two axes are published per date, because neither derives from
the other in general:

| `alert_state` | `coverage` | Means |
| --- | --- | --- |
| `alerts` | `complete` / `partial` | alerts found, all / not all of the extent observed |
| `zero_alerts` | `complete` | observed, nothing found — a positive observation of absence |
| `zero_alerts` | `partial` | nothing found where it could be looked, part could not be |
| `no_valid_coverage` | `none` | nothing observed at all |

`classify_date` is total over the contract's seven statuses (parametrised
test), and the single place the axes overlap — `no_valid_coverage` ⟺
`coverage == "none"` — is asserted so it cannot drift.

One measurement corrected a test premise mid-implementation: a
`complete_zero_alerts` row **does** seal an `artifact_sha256`, so a quiet day
publishes a real object. A first version of the tombstone test assumed a quiet
day published nothing; it was wrong, and the two reclassification paths are now
tested separately — a quiet day that gains alerts (`date_reclassified` against
the surviving object) and an unobservable day that gains alerts
(`date_reclassified` against the manifest, because there were no bytes).

## 3. Validation before promotion: composed, not duplicated

`check_green_release` **requires the ledger** and re-runs
`check_processing_ledger` on the bytes stored beside the release, so the
Package 2B.2A gate runs again at promotion time. The two halves of the roadmap
bullet that were unresolved:

- **Expected dates** come from the ledger's own manifest-bound expected set —
  the UTC dates of the expected acquisitions. A revisit calendar was rejected:
  it would be a second source of truth and would fail closed on legitimate
  cloud or rejection gaps the ledger already represents as terminal states.
  Every reconciled date must appear exactly once, in chronological order, and
  no other date may appear. That is the partial-release clause at the date
  level.
- **The state watermark** is `finalized_through`, the latest date whose every
  expected acquisition is terminal and whose summary reconciles — **derived,
  never supplied**, so a caller cannot overclaim it.

`verify_release` then **re-reads** every declared object and compares size and
checksum. A `PutObject` that returned 200 is not proof the bytes a consumer
will fetch are the bytes declared.

### A fail-closed check I did not write

The obvious watermark check — refuse when `finalized_through <
coverage.last_observed_on` — is **unreachable**: the gate guarantees every
expected date reconciles, and `dates[]` is exactly that set, so the two are
equal by construction. Writing it would have been the 2B.2A mistake in a new
place: a branch that looks like protection and can never fire.

The reachable form of the same concern is *across* releases, and that is the
coverage-regression rule in §5. The state watermark and "an older run may not
replace a newer release" turn out to be the same property.

### Deliberate non-requirements

Recorded in `GREEN_RELEASE_CONTRACT_V1.md` §4, each because the producer does
not promise it:

1. **No claim about the persistence state's contents.** Its digest and length
   are provenance. In particular `max(last_seen)` is **not** a watermark:
   `update_tracks` overwrites `last_seen` with the date being processed and a
   run re-covering the 16-day window moves it *backwards*
   (`test_last_seen_can_move_backwards`). Asserting monotonicity there is the
   2026-09-07 outage. `test_the_watermark_makes_no_claim_about_the_state_contents`
   publishes two releases differing only in that digest and requires both to
   be accepted.
2. **No requirement that every sealed artifact be published.** The contract
   guarantees such an artifact *exists*, not that a publication includes it,
   and a release of date-level products only is a permitted shape. The CLI
   reports coverage and offers `--require-sealed-artifacts` for pipelines that
   do produce one artifact per acquisition.
3. **`artifact_sha256` is never read for the five rejection/failure statuses,**
   where the schema leaves it unconstrained. An object may not claim
   provenance from such an acquisition, and the value is not even compared.

## 4. Conditional writes — and a measured correction to the briefing

Briefing §2h carried Cloudflare's recipe for per-request custom headers:
register `before-parameter-build.s3.PutObject` and `before-call.s3.PutObject`
and move the header into the request context, because botocore rejects unknown
arguments.

**Measured before building on it: the general warning is true, and it does not
apply to these two parameters.** `ParamValidator` on the real `PutObject`
input shape reports *Unknown parameter in input: "ExtraHeaders"* — pinned as a
negative result in `test_an_arbitrary_extra_argument_really_is_rejected` — but
`IfMatch` and `IfNoneMatch` are **native members** of that shape in botocore
1.42.42, because AWS S3 gained conditional writes after the Cloudflare example
was written. The preconditions therefore travel as ordinary parameters and this
package reaches into no botocore internals: fewer moving parts, and no reliance
on private event-system plumbing.

This is a mechanism detail, not the scope decision of briefing §4, which was
not reopened.

`require_conditional_write_support` keeps it from becoming a silent
assumption, and it is **not** a duplicate of botocore's own validation: it asks
the loaded service model *before any object is touched*, because the failure
mode it guards is an unconditional `PutObject` that overwrites silently. The
branch is reachable — the shape comes from botocore's data files, not from a
file this repository pins — and is tested with a client whose model lacks the
members.

**An ETag is a compare-and-swap token, never a checksum.** Single-PUT ETags are
the body MD5; multipart ETags are the MD5 of concatenated part MD5s with `-N`.
The store reads it, keeps it, hands it back in `If-Match` and parses nothing;
`test_an_etag_is_never_treated_as_a_content_checksum` drives a fake whose ETag
is a `-7` composite. Copy-time destination conditions
(`cf-copy-destination-if-match`) are in beta and nothing is built on them.

`CopyObject`, `DeleteObject` and an unconditional `put` are simply absent from
`ConditionalStore`. The fake store **raises** on an unconditional `PutObject`,
so every test that goes through the store also proves no code path writes
without a precondition.

## 5. Two axes, and the order that makes publication atomic

The order is the mechanism: objects first under the immutable prefix, the
manifest **last**, then every object re-read and verified, and only then one
compare-and-swap on the pointer. A run that dies at any earlier step leaves the
previous release live and complete. Bullets 3 and 4 are the same property from
two sides.

`sequence` counts pointer **writes** and only ever increases, rollback
included. `coverage.last_observed_on` says what **data** the release covers.
Conflating them is the trap: **a replay of an old window is a later write of
older data**, so any recency test based on sequence or clock would wave it
through. `promote` compares coverage and refuses a strict regression
(`coverage_regression`); equal coverage is not a regression.

`promote` has **no override flag** — `test_promote_has_no_regression_override`
asserts that from the signature. Going backwards is `rollback`, a named
operation recorded as `action: "rollback"` with `rolled_back_from`, which
re-reads and fully revalidates its target from the store (including its
ledger) and verifies every object is still present. The pointer may only ever
name a release that is still complete.

A failed precondition is **never retried**: the decision behind the write was
made about a version that is no longer live. The CAS sits *behind* the
serialized lane, not instead of it — concurrency groups are per repository, so
a local run or a re-dispatch from another ref is outside the lane.

## 6. Tombstones live on the pointer

Staleness is a **relation between two releases**, not a property of either: a
release is immutable and is built before anything is known about what it will
supersede, and what is stale depends on which release is live when it is
promoted. The pointer is the only object that knows both. Three reasons kept
distinct — `absent_from_successor`, `superseded_content`, `date_reclassified` —
with the third being the one that matters scientifically, because a replay
that retracts a date's alerts must never be silent. **Nothing is deleted;**
retention is Package 2B.3.

### Two defects my own first drafts had, and how they were caught

Recording these because both are the class of error this package exists to
prevent.

1. **The CLI guessed intent by checksum.** `--object` matched a body against
   the ledger's sealed checksums and, on no match, silently labelled it a
   `date_product`. So a *tampered alert artifact* passed validation as a
   different kind of object. Caught by running the plan against a deliberately
   corrupted file and seeing it succeed. Replaced with explicit `--artifact`
   (must match a sealed checksum on its date, mismatch is fatal) and
   `--product` (no ledger claim). Guessing conflated two things the contract
   distinguishes.
2. **Four lane tests scanned heredoc prose as if it were code.** The refusal
   message legitimately tells an operator to run `publish_green_release.py
   apply` locally, and a naive substring scan read that as the lane performing
   a mutation. The test method was wrong, not the lane: `executed()` now strips
   heredoc bodies and comments, so the assertions read what the shell runs.
   A test that passes for the wrong reason is worth as little as one that
   fails for the wrong reason.

## 10. What the P2B exit gate still needs

The gate reads: *a deliberately failed or racing green run cannot corrupt blue
or expose a partial release; a staged test release can move and roll back its
green pointer without a manual data PR or any production effect.*

**Closed by this package, in code with tests:**

- *cannot expose a partial release* — the manifest is written last, every
  declared object is re-read and verified, and the pointer moves in one
  compare-and-swap only afterwards. A partial publication provably leaves the
  previous release live and complete.
- *a racing green run cannot corrupt* — `If-None-Match: *` on every immutable
  write with a byte comparison on `412`; `If-Match` on the pointer with no
  retry; a coverage-regression refusal so a replay of an old window cannot
  replace a newer release.
- *move and roll back the pointer* — `promote` and `rollback`, with rollback
  revalidating its target from the store and refusing a release that is no
  longer complete.
- *cannot corrupt blue* — no code path here can address `araripe-cogs`;
  `assert_staging_target` refuses it by name before a credential is read, and
  no blue workflow file changed.

**Still open:**

- **The gate's clauses are proven against a fake store, not against R2.** That
  is deliberate and was forced: the `v2-staging` Environment's deployment
  branch policy admits only `main`, so nothing on a feature branch can reach a
  staging credential. The design had to be right *before* it was executable.
  The real-object proof needs the merge first, and then the protected
  promotion identity.
- **"without a manual data PR"** is only half answered. Publication now targets
  R2 rather than a git path, so no `detect_gee.yml` publish guard was touched —
  but wiring the *scheduled* flow to it is **Package 2B.2C** and is not
  started.
- **Package 2B.3** — private/public R2 boundary, least-privilege credentials,
  the staged `/data/...` route, retention and deletion policy. Tombstones are
  recorded here and nothing is ever deleted; deletion policy is 2B.3's.
- **Package 2B.4** — green site artifact and deployment.
- **The Package 2B.0 lane proof** — four concurrent runs, four recorded URLs.
  Now dispatchable (`mode=lane-proof`, and the workflows have been on `main`
  since `8daa1812f8c2f89d6fa13be44c38283242c103bd`). Still a 2B.0 gate item,
