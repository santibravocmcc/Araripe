# Package 2B.1 — state safety and workflow coordination

**Started:** 2026-09-06
**Base:** `origin/main` at `58f5bb8273adce93d2a3cafabb447b5e36ea1837`
**Branches:** `claude/phase2b1-state-safety` (backend),
`claude/phase2b1-site-freshness` (site)
**Production impact:** none. No R2 write, no workflow dispatch, no Cloudflare
operation, no broker use, no Environment approval. Both changes are staged in
pull requests and neither is merged.

## Why this package exists

Every one of the four roadmap bullets is the same defect in a different place:
**something assumes another system succeeded, and nothing re-checks it.** The
assumption is invisible while it holds, and when it stops holding the failure is
silent — a green run that published nothing, or worse, published something
wrong.

## 1. Fail closed when the R2 state cannot be trusted

`scripts/r2_state.py` wrapped its download in a bare `except Exception` that
printed `no persistence_state.geojson in R2 (primeira execução?)` and continued.
Authentication failure, network error, truncated download and corrupt object
were therefore indistinguishable from a genuine first run, and the pipeline
proceeded with an **empty** state — resetting `n_sightings`, `first_seen` and
`last_seen` for every track. Those counters are the scientific product: they
drive `first_observation` / `candidate` / `confirmed`, they only ever grow, and
after a reset nothing downstream can tell the difference between a wiped state
and a genuine wave of first observations. Recovery needs a full replay.

`get` now admits exactly one benign outcome. A real `404`/`NoSuchKey` is a first
run. A `403`, a denied or expired key, a missing bucket, a network failure, a
body whose length disagrees with the object's `ContentLength`, unparseable JSON,
or a payload that is not a track `FeatureCollection` all fail closed and write
no file. `403` is deliberately *not* absence: it hides existence rather than
denying it. The download lands on a `.part` file and only a fully validated
payload is moved into place, so a rejected fetch cannot damage a good local
state.

`--require-existing` closes the last gap. This deployment's state does exist, so
an absent object means deletion or a wrong bucket/endpoint, not a first run.
Both blue workflows pass the flag; omitting it remains the way to bootstrap a
new deployment.

`put` no longer exits 0 when the local file is missing — that turned "detection
produced no state" into a silent no-op that left the previous state live while
reporting success — validates the payload before upload, and confirms the stored
size afterwards.

Two further paths reset the tracks just as silently, one layer down, and are
fixed here too:

- both detection scripts caught every read error and continued with
  `state = None`, so a corrupt-but-present file still started from zero. They
  now call `load_persistence_state()`, which returns `None` only for a genuinely
  absent file and raises `PersistenceStateError` otherwise;
- `run_detection.py` swallowed a failed state **save**, leaving the run green
  with the previous state on disk — which the following `r2_state.py put` then
  re-uploaded, discarding that run's updates without any signal.

## 2. One serialized lane for the blue state writers

`detect_gee.yml` declared no `concurrency:` at all, and neither did
`update_data.yml`. Both read-modify-write the **same** R2 object, and detection
is not idempotent: a second overlapping run inflates `n_sightings` for every
track it re-observes.

Both files join **one** group, `araripe-legacy-state`, with
`cancel-in-progress: false`. One group rather than two is the point: GitHub
scopes implicit concurrency to each workflow *file*, so separate groups would
serialize each file against itself and still permit exactly the cross-file
interleaving that matters — a manual fallback dispatch during a scheduled run.
`update_data.yml`'s own header already warned that running both "would
double-detect and fight on push"; nothing enforced it.

Never cancelling is the safe direction here: alerts are uploaded to R2 *before*
the state is, so a killed run can leave published alerts whose track updates
never landed.

The green lanes from Package 2B.0 keep their own groups, so a long green replay
can neither block nor be blocked by a blue schedule.
`docs/operations/GREEN_CONCURRENCY_LANES.md` records that this supersedes one
sentence of the 2B.0 lane definition ("concurrency key: none declared"), why,
and GitHub's queue semantics — at most one running plus one pending run, so a
third concurrent trigger is dropped rather than queued, which
`SEARCH_DAYS_BACK = 16` makes self-healing.

## 3. A validated release signal instead of a clock offset

**The documented cadence divergence did not exist.** The task premise — backend
`0 6 * * 1,4` and site `30 7 * * 1,4`, 90 minutes apart, contradicting
`AGENTS.md` — was read from the site branch `codex/workspace-consolidation`,
which predates two squash-merged pull requests. On the site's `main` the cron
has been `0 6 * * 2,5` (Tue/Fri 06:00 UTC) since PR #13 (`01564f6`), a real 24 h
gap, exactly as the workspace `AGENTS.md` says. PR #14 (`b9b8120`) merged the
Earthdata transient-skip fix. Both source branches still read as unmerged by
ancestry because they were squash-merged.

The stale artifact was this repository's `ROADMAP.md` §6, which still carried a
"**Pending:** … is NOT merged" note; it is corrected. That staleness is itself
the package's theme one level up: a claim about another system's state that
nothing re-checks goes quiet when it stops being true.

So the 24 h gap stays, but it stops being what correctness rests on. Every
successful backend run writes `data/timeseries/RELEASE.json`
(`scripts/write_release_signal.py`) recording the run identity, the publication
time, the latest observation date, and the SHA-256 and size of `timeseries.db`.
It is written *into* `data/timeseries/`, so it rides the existing publish lane
untouched — that step already refuses to stage anything outside that directory —
and is squash-merged in the same commit as the DB. Atomicity comes from the lane
rather than from new machinery.

Before preparing data, the site validates it
(`site/scripts/check_backend_release.py`): the signal exists, parses, carries the
expected schema, the `timeseries.db` in its clone matches the declared checksum
and size — which is what proves the two came from the same commit rather than
from a `main` read mid-PR — and the publication is not older than 10 days. Any
of those failing stops the run instead of silently republishing a stale series.

The signal is rewritten on **every** successful run, including runs where the
series did not change. A signal that only advances with the data cannot separate
"healthy but quiet" from "broken for a week", which is precisely the distinction
the consumer needs. The cost is one small commit per run.

`RELEASE.json` is seeded on the backend branch from the committed
`timeseries.db`, whose checksum it matches, so the site's checksum gate holds
from the moment the backend PR merges. It records no run id, because no run
produced it.

**Merge order is load-bearing:** the backend lane must merge and run at least
once before the site change reaches the site's `main`. Otherwise the site's
first scheduled run finds no signal and fails — loudly and harmlessly, since it
publishes nothing, but avoidably. `ARARIPE_RELEASE_SIGNAL_OPTIONAL=1` is the
explicit, recorded escape hatch for that window.

## 4. Alerts and rainfall, independent

`chuva` declared `needs: alertas`, so any alert-side failure skipped rainfall
entirely — although the products are unrelated (GPM/Earthdata versus R2 plus the
Araripe repository). The dependency existed only to avoid a push race, and both
jobs already had rebase + retry over disjoint paths. Removed.

Independence is only safe if each product can say when it was last genuinely
updated, because nearly every "skipped" path exits 0 and leaves the run green.
Rainfall had half a guard (`MAX_DIAS_SEM_ATUALIZAR` in `fetch_gpm.py`) that
applied only on the Earthdata-unreachable path — the *incomplete week* path
returned without checking anything, so consecutive incomplete weeks froze the
rainfall silently. Alerts had none.

Each product now writes `public/data/freshness/<product>.json` with
`updated_utc` (last real production), `checked_utc` (last time a run looked),
the status, and why it skipped. The mechanism rests on one distinction:
**`skipped` advances `checked_utc` but not `updated_utc`**, so "quiet" stays
distinguishable from "broken". `fetch_gpm.py` records all three `--write`
outcomes — wrote, incomplete week, URS unreachable — because it is the only
place that can tell them apart.

Each job ends by checking its own freshness with `if: always()`: it is exactly
when a run fails that the product may have aged past its budget. Budgets are 10
days for alerts and 21 for rainfall (the already-reviewed
`MAX_DIAS_SEM_ATUALIZAR`, now applying on every path). Before the first record
the step warns rather than fails; that bootstrap clears itself on the first
successful update.

Separate files per product are deliberate: with both jobs running in parallel,
disjoint paths rebase without conflict. The workflow also gains
`concurrency: site-update-data`, `cancel-in-progress: false`, so two overlapping
runs cannot multiply the push race.

## Boundaries observed

- The backend `main` is untouched: work is on a branch, PRs are open, nothing
  merged, no ruleset or repository setting changed, no bypass actor added.
- Production is untouched: no write to `araripe-cogs`, no workflow dispatch, no
  Worker/DNS/route/domain/pointer change, no broker operation, no Environment
  request.
- `detect_gee.yml` was never dispatched. It is not idempotent — a manual re-run
  inflates `n_sightings` in the R2 `persistence_state` — so the concurrency and
  `--require-existing` changes are verified statically, from the workflow files.

  `data/landcover/updated/`, `data/validation/`) were left untouched and unstaged.

## Requires explicit human approval before merge

1. **`detect_gee.yml` and `update_data.yml`** — blue workflow files. The
   concurrency lane, `--require-existing`, and the release-signal step all change
   how the live scheduled pipeline behaves. Nothing in them touches credentials,
   schedules, or the publication route.
2. **Merge order** — backend PR first, then at least one backend run, then the
   site PR. See §3.

## What the P2B exit gate still needs

The gate reads: *a deliberately failed or racing green run cannot corrupt blue
or expose a partial release; a staged test release can move and roll back its
green pointer without a manual data PR or any production effect.*

Package 2B.1 contributes the "cannot corrupt" half for state and coordination:
blue state operations fail closed, the blue state writers are serialized, and
the consumer validates a release instead of assuming one. It does **not** close
the gate. Still open:

- **Package 2B.2** — manifest, ledger, atomic publication, conditional writes,
  explicit zero-alert dates and tombstones. The gate's "partial release" clause
  lives here, and it cannot close before integration with the Package 2A.6
  producer/consumer passes. 2A.6 is closed on `claude/phase2a6d-mapbiomas` and
  is not on `main`.
- **Package 2B.3** — private/public R2 boundary, least-privilege credentials,
  staged `/data/...` route against the isolated staging Worker.
- **Package 2B.4** — green site artifact and deployment, automatic publication
  without bot pushes, pinned actions and locked environments.
- **The pointer half of the gate** — moving and rolling back a green staging
  pointer needs the 2B.2 publication contract; `v2_promotion_lane.yml` is still
  the 2B.0 placeholder.
- **The runnable lane proof** from 2B.0 (four concurrent runs, four URLs
  recorded) still awaits the v2 workflows reaching the default branch through a
  reviewed merge. This package adds the static half in
  `tests/test_workflow_lanes.py`.
