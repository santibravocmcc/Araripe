**O filtro de nuvem é 60, não 20.** `MAX_CLOUD_COVER = 20` só é lido pelo
caminho STAC (`run_detection.py`), que nenhum fluxo agendado roda. Os dois
caminhos reais têm `--max-cloud` com padrão 60 (`replay_2026.py` no verde,
`run_detection_gee.py` no azul) e nenhuma lane o sobrescreve. Depois vem a
máscara SCL por pixel e o portão da data: cobertura válida < 20% ou > 30% da
área válida marcada (`scene_quality.assess_scene_quality`).

Os números passaram a viver em `site/worker/metodo.js`, e
`site/tests/texto_do_metodo.test.mjs` lê cada um na fonte do backend. Uma
consequência para quem mexer no backend: **mudar uma dessas constantes
derruba um teste do site**, de propósito.

## 4. O desenho — escrito antes do código

**Um campo aditivo no índice: `unanalyzed_dates`.** Cada item é
`{"date": "YYYY-MM-DD", "reasons": [...]}`. Nada mais: sem feições, sem
estatística, sem entrar em `totals` nem em `last_run`.

- **Quais datas:** exatamente as de `alert_state == "no_valid_coverage"`. É
  `green_release.classify_date` quem promete que isso equivale a nenhuma
  aquisição com status selador, e quem define o conjunto é a release — o site
  não mantém lista.
- **`reasons`:** as chaves de `status_counts` com contagem > 0, em ordem
  alfabética. O vocabulário é o do produtor (`ledger_v3.TERMINAL_STATUSES`
  menos os dois `complete_*`), não um código inventado aqui. Uma chave
  `complete_*` com contagem > 0 numa data sem cobertura contradiz
  `classify_date` e é recusa, não descarte.
- **Por que "sem análise" e não "recusadas":** o conjunto inclui `failed_*`,
  que é falha, não recusa. Hoje são 0; o nome não pode mentir quando
  deixarem de ser.
- **Onde mora a regra:** `src/publication/site_artifact.unanalyzed_date` no
  backend, uma função pura de uma entrada de `dates[]`. O site a porta, como
  já porta o resto, e um grupo novo de vetores, `date_cases`, prende as duas.
- **Contrato:** continua `araripe.site.alert_index/1`. O campo é opcional no
  schema (um índice antigo continua válido) e os dois compositores o emitem
  sempre, vazio quando não há data. Nenhum índice `/1` foi publicado para o
  público ainda (§9 do contrato; o índice é derivado a cada build), então não
  há consumidor antigo a quebrar. `stats_policy_version` não muda: nenhuma
  estatística mudou.
- **O compositor recebe a lista como argumento obrigatório.** Com padrão
  vazio, um chamador que esquecesse de passá-la produziria de novo o defeito
  que isto conserta — a data sumindo — sem ninguém saber.
- **O validador acrescenta quatro relações**, que o schema não expressa:
  datas em ordem, sem repetição, disjuntas de `runs[]`, e `reasons` em ordem
  canônica (o índice é reprodutível byte a byte, §4 do contrato).
- **Na página:** só na visão verde. O seletor de período continua com as
  execuções; as datas sem análise vão numa lista própria, recolhida, com o
  texto do motivo escrito pelo site a partir de `worker/metodo.js`. No azul
  nada muda: o manifesto azul não tem o campo.

**Fora deste desenho, de propósito:** aquisições recusadas numa data que teve
outra utilizável (`coverage = "partial"`, 15 datas). A data foi analisada; o
que faltou nela é outro assunto e não foi pedido.
