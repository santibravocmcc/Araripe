## Purpose

Package 2B.0 makes blue/green isolation explicit before any state, workflow,
publication, Worker, or site migration. The current blue system remains the
production fallback until the separately approved cutover. Green components
use distinct credentials, resources, workflows, and deployment targets and
cannot promote a canonical release.

## Risk-based approval policy

- Autonomous (no repeated approval): local development and alternative local
  branches; object operations in `araripe-v2-staging`; manual green workflows
  holding only the staging-scoped identity; read-only verifications; commits,
  branch pushes, and opening pull requests; merging a minimal, additive,
  inert pull request proven not to change blue runtime files.
- Explicit human approval is mandatory for any action with authority or
  potential effect on production: blue workflows, the production Worker,
  `araripe-cogs`, the final public domain, DNS, routes, canonical pointers,
  the public site, cutover steps, and any Cloudflare token with account-level
  edit permission.
- `v2-staging` needs no reviewer (bucket-scoped identity).
  `cloudflare-green-control` keeps its required human reviewer because its
  token carries account-level edit permission. No agent approves its own
  Environment run or bypasses a pending approval, failure, or broker refusal;
  a missing broker operation means stop and safe handoff, never Wrangler,
  `curl`, direct API, or a different credential.

## Exit gate

Package 2B.0 closes only when: staging credentials succeed on the staging
bucket and are denied on production; site non-production branch behavior is
proven safe; the staging Worker has no production route; v2 workflows cannot
run on a schedule or mutate legacy resources; green credentials have no
blue/public-promotion authority; and the safe-handoff skill passes structural
and execution tests in both tool discovery paths. Until then, only read-only
design and non-mutating local preparation for Package 2B.1 may proceed.
