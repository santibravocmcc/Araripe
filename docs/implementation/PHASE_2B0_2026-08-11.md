## Purpose

Package 2B.0 makes blue/green isolation explicit before any state, workflow,
publication, Worker, or site migration. The current blue system remains the
production fallback through Phases 2B–5. Green components use distinct
credentials, resources, workflows, and deployment targets and cannot promote a
canonical release until Phase 6.

## Credential decision

Claude Code receives only an R2 S3 `Object Read & Write` credential scoped to
the exact bucket `araripe-v2-staging`. It must not receive
`CLOUDFLARE_API_TOKEN` in the production account. The user must create the R2
credential once in the Cloudflare dashboard and save it as the local AWS profile
`araripe-r2-staging`; the one-time secret must never enter an agent transcript.

Exact setup and acceptance tests are in
`docs/operations/CLOUDFLARE_STAGING_ACCESS_FOR_CLAUDE.md`.
AWS CLI v2.36.20 was installed locally through Homebrew and verified on
2026-08-11; no R2 profile or credential was created.

The bucket credential permits object operations only. Bucket configuration,
Workers, routes, DNS, Builds, bindings, token creation, and promotion remain
Codex/Cloudflare-control-plane tasks. A missing capability invokes the
versioned `araripe-safe-handoff` skill rather than a broader credential.
The current resume checkpoint is
`docs/handoffs/20260811T200410Z_phase2b0-r2-credential.md`; the earlier
credential checkpoint remains immutable audit history.

## Cross-tool recoverability implemented

The canonical skill is stored at
`.agents/skills/araripe-safe-handoff/SKILL.md` and exposed to Claude by the thin
adapter `.claude/skills/araripe-safe-handoff/SKILL.md`. It requires:

- target/capability classification before mutation;
- exact credential and environment preflight;
- immutable writes and no partial pointer/ledger promotion;
- a durable, exclusive checkpoint under `docs/handoffs/` when blocked;
- explicit user notice naming the missing capability;
- a self-contained Codex handoff prompt;
- branch/commit/cloud-state revalidation before resume.

The helper accepts only bounded, owner-only mode-`0600` JSON under
`/private/tmp`; rejects duplicate keys, common/opaque secret forms in payload or
Git branch identity, unsafe controls, and symlink escapes; neutralizes inline
HTML/Markdown; and stops Git capture at the configured bound. Suspicious opaque
Git path components are replaced with labelled SHA-256 digests, with only the
exact expected checkpoint path exempted. It records repository state
immediately before installation and the checkpoint path as the exact expected
delta. A complete temporary copy is fsynced and installed once
through an exclusive hard link; an existing target is never replaced, and the
directory is fsynced after installation.

## Blue resources that remain unchanged

- backend schedules and manual fallback on the production default branch;
- site data-refresh schedule and existing bot-generated Git data;
- `araripe-cogs` and its fixed legacy prefixes/state objects;
- production Worker `observatorio-chapada`;
- Worker Builds integration from the site repository;
- final apex domain and routes.

This is intentional. The candidate backend branch already contains scientific
changes, including the five-day window. Merging it wholesale would make the old
scheduled workflow run candidate science against production state. That is
forbidden.

## Remaining Package 2B.0 work

1. User creates and locally stores the one-bucket Claude R2 credential.
2. Verify allowed list/put/get/delete in `araripe-v2-staging` and denied access
   to `araripe-cogs` without revealing values.
3. Re-audit current Cloudflare Worker Builds branch behavior before any site
   candidate-branch push; non-production branch builds were enabled in the last
   inventory and preview isolation was not proven.
4. Define a distinct staging Worker/environment with no apex/custom route and
   its own R2 binding/rate-limit namespace.
5. Create separate GitHub Environment `v2-staging` and a different bucket-only
   Actions identity; do not reuse Claude's identity.
6. Introduce new v2 workflows in an inert/manual route that cannot be triggered
   by existing production schedules. GitHub manual-dispatch/default-branch
   constraints must be handled without merging executable candidate science
   into the old schedule.
7. Define three concurrency lanes: legacy live mutation, green candidate/replay,
   and serialized green staging-pointer promotion.
8. Record an accepted before-state after the live recheck and pass the 2B.0 gate.

No new permanent repository is planned. Isolation uses branches, workflows,
GitHub Environments, credentials, buckets/namespaces, and a staging Worker. A
temporary private orchestration repository is permitted only if the existing
Cloudflare/GitHub default-branch integration cannot provide demonstrably inert
manual execution.

## Exit gate

Package 2B.0 closes only when:

- Claude's token succeeds on the staging bucket and is denied on production;
- site non-production branch behavior is proven safe;
- the staging Worker has no production route;
- v2 workflows cannot run on a schedule or mutate legacy resources;
- green credentials have no blue/public-promotion authority;
- the safe-handoff skill passes structural and execution tests in both tool
  discovery paths.

Until then, only read-only design and non-mutating local preparation for 2B.1
may proceed. No 2B.1 implementation, remote activation, or gate claim is
allowed before 2B.0 closes.
