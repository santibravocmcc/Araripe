## 1. The boundary: public is the live release, not `releases/`

`araripe-v2-staging` holds `runs/<run-id>/` and `releases/<id>/` side by side
and has no public access of its own, so the boundary is not the bucket — it is
whatever a Worker serves. `src/publication/delivery_boundary.py` is the only
place that decides, and the contract is
`docs/contracts/phase2b/GREEN_DELIVERY_BOUNDARY_V1.md`.

The decision that mattered was **not** "runs private, releases public". Serving
`releases/` would publish exactly the two things the publication design refuses
to serve, and both are in the bucket right now:

* `rel-g1-9f1ed3441310bd632caba3e5354cb20707669b433bf3a75e42db4a1bc245f54e` —
  promotion **refused** for `coverage_regression`. Its objects were written,
  correctly, because publishing is safe and only promotion has a gate.
* `rel-g1-5ffad23ad2b4072fa63f01b86fdab4f3f34627fddd0f877f910e7a4544d77d37` —
  live at `sequence 2`, **rolled back away from**.

"Published" and "live" are different states, and only the second is public.

### The key is never built from the request

The path after the mount is looked up in an allowlist built from the live
manifest's `objects[].path`, and the key is `release_prefix + that declared
path`. `runs/`, a probe prefix and another release are unreachable because
those strings never enter a key. That is why every miss returns one code —
`not_declared_by_the_live_release` — for `../../etc/passwd`,
`runs/proof-a/run.json` and a plain typo alike. A denylist would have to
imagine the first two and would still be a denylist.

Mutation-proven: replacing the allowlist lookup with a pass-through fails 14
tests in `test_anything_the_live_release_does_not_declare_is_refused` and the
vector check, and nothing else.

### `content_type` is validated because the producer promises nothing

`green-release-v1.schema.json` constrains `path` with a strict `logical_path`
pattern and `sha256` with a hex pattern, and leaves `content_type` as
`{"type": "string", "minLength": 1}`. A CR or LF in it splits the response, so
the route validates it as a media type before a header carries it. This is the
`LEDGER_CONTRACT_BINDING_V1.md` §5 rule read the other way: never assert an
invariant the producer does not promise, and never rely on one either.

### The mount is `/data/green/`, not `/data/`

The site serves `/data/alerts/manifest.json`, `/data/territorio/…` and
`/data/educacao/…` as static assets today. A mount at `/data/` would shadow
them and switch every consumer the moment it deployed — the opposite of the
bullet *copy and verify before switching consumers; retain the old paths for
rollback*.

### Conformance vectors, because two implementations of one policy drift

The authority is Python; the thing that will answer a request is a Worker, in
JavaScript. `docs/contracts/phase2b/delivery_conformance_vectors.json` holds a
fixture and 14 request/outcome cases. Neither implementation is the reference —
the vectors are, and a policy change that forgets to regenerate them fails the
gate. Same division as Package 2B.2A: the schema owns shape, the code owns the
relations shape cannot express, and neither restates the other.

## 2. Retention: the store has no promotion history

`src/publication/retention.py` produces a plan and **cannot delete**, and
neither can anything it imports —
`test_no_deletion_is_expressible_from_the_retention_path` reads that from the
files by AST rather than promising it.

Three dispositions: `retain`, `review`, `eligible`. `review` — "the store does
not contain what a decision would need" — is the point. A two-way policy has to
answer every question, so it answers some of them by assumption.

**The finding that shapes everything.** `pointers/green/current.json` is one
mutable object, overwritten on every move, carrying one step of context. Read
from the real bucket (ETag `6d251a1d33d3ce5f5ca72690368fa963`) at `sequence 3`:
`supersedes` and `rolled_back_from` both name `rel-g1-5ffad23a…`, and
`rel-g1-9f1ed344…` appears nowhere.

So the two cases the briefing distinguishes are distinguishable **today**, and
stop being so after one more pointer write: `rel-g1-5ffad23a…` drops out and
becomes indistinguishable from a release that was never live. Since a
formerly-live release is the natural rollback target, "delete every release the
pointer does not reference" would delete precisely the one an operator would
want back. `test_a_release_that_was_live_becomes_undecidable_after_one_more_move`
is that as an executable fact.

**Therefore no release is ever `eligible`**, proven as a property over every age
with every option enabled (`test_no_release_is_ever_eligible_at_any_age`).

### The prerequisite, specified and deliberately not built

A durable write-once promotion history — one immutable object per pointer write
— is what would make release retention decidable. It is **not** built here: it
would add a write to `atomic_publish.promote` and `rollback`, and that path was
proven end to end against real R2 five times on 2026-09-07. Changing it means
those proofs no longer cover the code that runs. Build it, re-prove it, then
extend the policy — that is a package of its own.

### A run prefix's release is recomputed, never read

Nothing in the store records the link: a manifest carries the *ledger's*
`run_manifest_id`, not the `runs/<run-id>/` prefix. It is derivable because the
release identity is a pure function of the ledger, and the planner derives it
by running the same Package 2B.2A gate — so a ledger that would be rejected
yields no link and the prefix stays in `review`.

### A ripe run prefix still needs a named decision

A published release holds the ledger and the objects it published — never
`run.json`. And `GREEN_RELEASE_CONTRACT_V1.md` §4 non-requirement 2 says a
release need not publish every sealed artifact, so "the release is complete"
does not mean "everything here survives elsewhere". The planner states the loss
and requires `--accept-run-manifest-loss` rather than defaulting it.

### The reviewed dry-run

    python scripts/plan_retention.py --as-of 2026-09-07T23:00:00Z

Over the real 29 objects: **26 retain, 3 review, 0 eligible**. The 3 are exactly
the refused release; the 4 `release_is_referenced` are exactly the
rolled-back-from one. Both kept, for different printed reasons — which is what
the roadmap asked the policy to distinguish. Full output and reasoning in
`docs/operations/GREEN_RETENTION_AND_MIGRATION.md` §4.

## 3. Least privilege — measured, including what cannot be narrowed

Read from Cloudflare's own documentation and confirmed by a real call.

* **Scoping is per bucket.** The Access Policy resource is
  `com.cloudflare.edge.r2.bucket.<account>_<jurisdiction>_<name>`. There is no
  prefix scoping, so the private/public boundary **cannot** be a credential.
* **There is no level between read and write, and write includes delete.**
  Measured, not inferred: `scripts/probe_readonly_identity.py --expect
  read-write` against the local bucket-scoped staging key (run id
  `local-2b3-measure-1`) reported five of five, including *"this identity holds
  DELETE inside the bucket — accepted on an absent key; nothing was
  destroyed"*. The delete was issued against a key that did not exist, and the
  probe refuses to target one that does.
* **Worker R2 bindings narrow nothing.** `r2_buckets` takes `binding`,
  `bucket_name` and `jurisdiction`, and the Workers API reference states a
  bound bucket can READ, LIST, WRITE and DELETE. No read-only binding, no
  prefix binding.
* **`Object Read only` exists and is bucket-scopable** — the one real
  narrowing.

So every identity able to publish a release is able to erase one. That single
measurement is why this package keeps deletion out of the code: if the
credential cannot be the boundary, the code has to be, and an absent operation
is the strongest boundary available.

### What is proposed, and why it is not wired

A third identity `v2-staging-readonly` at `Object Read only` for the `stage`
job, which reads operator-supplied input and today holds a key that could write
or delete any object in the bucket. Not a narrowing of `v2-staging` itself:
that would break the Package 2B.0 isolation probe's write step, and losing the
write half of that proof is a worse trade.

**Nothing in the repository names it.** GitHub does not fail on an unknown
environment name — it *creates* one "with no protection rules or secrets
configured", which is a repository configuration change and the wrong one. The
wiring waits for the Environment, exactly as 2B.2C waited for `v2-promotion`.

And when it exists, the scope is proven by **refusal**, not by configuration:
on 2026-09-07 a promotion key with a perfect Environment reached the production
bucket. `tests/test_readonly_identity_probe.py` asserts both polarities for
both operations — a successful write or delete must **fail** a `read-only`
probe — because an inverted check with the polarity wrong certifies exactly the
credential it exists to catch.

## 4. Step-level secret exposure, and the defect the sweep found

Every green workflow already exposed secrets at the step rather than the job.
The sweep found one thing that was not deliberate.

The `stage` job of `v2_operational_publish.yml` exported the candidate key
**twice**: as `R2_STAGING_*`, which `stage_green_run.py` reads and passes to
`boto3.client` explicitly, and as `AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY`, which nothing reads.

The unused pair was not inert: it put the credential into **boto3's default
credential chain**, so an AWS call that never went through `build_client` and
its bucket-and-endpoint guard would have been authenticated anyway — and by §3
that key writes and deletes across the whole bucket. Removed, and pinned by a
rule read from both files: a step running a repository script may export only
names that script reads.

**The blue lane does not have the job-level property**, and that is *recorded*
rather than fixed: `detect_gee.yml`, `update_data.yml` and
`esa_reprocessing_watch.yml` expose `R2_ACCESS_KEY`, `R2_SECRET_KEY` and
`GEE_SA_KEY` at the job, so every step of a blue run — including checkout —
holds them. Narrowing that is a blue change, frozen through Phase 6. Asserting
the current state means it cannot drift unnoticed meanwhile.

## 5. What could not be validated, and why that is the isolation working

The bullet says *prepare and validate a same-origin `/data/...` route against
the isolated staging Worker*. **The live validation could not be run.**

`observatorio-chapada-v2-staging` exists and already carries the right binding
(`STAGING_BUCKET` → `araripe-v2-staging`, plus `STAGING_LIMITER`). But
`public_subdomain_enabled` is `false`, `custom_domain_count` is `0`,
`route_count` is `0`, and `scripts/cloudflare_green_control.py::audit` asserts
all three **fail-closed**. There is no hostname at which to reach it.

Giving it one is a control-plane mutation that is not among the broker's three
allowlisted operations (`audit`, `enforce-worker-isolation`,
`disable-site-branch-deploy`), and `enforce-worker-isolation` exists precisely
to turn that subdomain back off — so the operation would make the broker's own
audit fail. Per the Package 2B.0 handoff rule the correct action is to stop and
name the capability, not to substitute `curl`, Wrangler, `gh api`, another
workflow or a broader credential.

So the route is pinned by vectors, and the missing capability is named in
`GREEN_RETENTION_AND_MIGRATION.md` §5 with the exact live checks that will run
once a hostname exists. **This is a genuine gap in the roadmap bullet, and it is
recorded as one rather than papered over.**

Related and worth knowing: the site's `main` branch deploys the **production**
Worker `observatorio-chapada` through its Worker Builds production trigger. So
adding a `/data/...` route to `site/worker/index.js` is a production
deployment, not a staging one — another reason the Worker belongs to Package
2B.4 with its own deploy path.

## 6. What was deliberately not built

- **No delete capability, anywhere.** The roadmap says *do not delete during
  initial migration*, and the migration has not started: no consumer reads the
  green route because there is no route. Introducing the capability now would
  add risk with no corresponding gain.
- **No promotion history**, for the reason in §2.
- **No JavaScript.** The Worker is 2B.4's, and a node-dependent test in a
  pytest gate would be a test that can pass for the wrong reason on a machine
  without node. The vectors are the contract the Worker meets instead.
- **No change to the site repository**, no change to `data/timeseries/RELEASE.json`,
  and no cron on any green lane.
- **No immutable release-addressed URL namespace.** It would allow a year of
  caching and would make every non-live release publicly addressable, which is
  the one thing the boundary exists to prevent.

## 9. What the P2B exit gate still needs

The gate reads: *a deliberately failed or racing green run cannot corrupt blue
or expose a partial release; a staged test release can move and roll back its
green pointer without a manual data PR or any production effect.*

**Both clauses were already closed in execution on 2026-09-07**
(`GREEN_PROOFS_2026-09-07.md` §6 and §7) and this package does not touch them.
It adds a clause the gate does not name but the phase needs — *a green run
cannot expose what it was not promoted to expose* — and closes it in code and
vectors, not in execution.

**Still open for Phase 2B:**

- **A real 2A.6 producer run.** Nothing in production emits a v3 ledger, so
  every run so far was assembled by hand. The roadmap already makes this a gate
  condition.
- **Automatic run assembly.** The lane consumes `runs/<run-id>/`; a person
  still builds one.
- **The live route check** (§5), blocked on a reachable staging hostname.
- **Package 2B.4** — the green site artifact, the Worker that implements these
  vectors, and the green deployment.
