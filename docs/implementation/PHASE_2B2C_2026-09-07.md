## 1. Where the input comes from — the question 2B.2B left open

The publication path consumes a v3 ledger and artifacts whose checksums it
seals. **Measured: nothing in runtime emits one.** `src/detection/ledger_v3.py`
exists only on `claude/phase2a6d-mapbiomas`, and no `run_detection*.py` on
either `main` or that branch imports a ledger module at all (`grep` over the
three entry points, both refs).

The briefing left the choice open — emit in the green run, or accept an
artifact from an earlier run — with one rule: **do not invent a second ledger
producer.**

**Decision: accept a run's outputs from its immutable prefix in the staging
bucket.** Emitting would require either merging the 2A.6 producer into `main`
— which the briefing says is not needed, the consumed contract being already
pinned — or writing a second producer, which is forbidden. So the lane
*locates* a ledger; it never makes one.

The location was not invented either. `GREEN_CONCURRENCY_LANES.md` has
reserved it for lane 2 since Package 2B.0: *"immutable per-run prefixes only
(`green-isolation-proof/run-<id>/`, later `runs/<run-id>/…`)"*.

### `run.json` is the operator's command line, not a second ledger

`docs/contracts/phase2b/schemas/green-run-v1.schema.json` carries exactly what
`scripts/publish_green_release.py` already takes as `--ledger`, `--artifact`,
`--product`, `--date`, `--state-sha256` and `--state-bytes`. It defines no
scientific fact: every checksum trusted still comes from the ledger it points
at, `check_processing_ledger` runs on that ledger, and `check_green_release`
runs on the assembled release.

The test that makes this concrete is
`test_the_release_identity_comes_from_the_ledger_not_from_the_run`: two
different runs offering the same ledger and the same bytes produce the **same**
release id and the same manifest. The run document cannot influence identity,
so republishing stays a byte-exact no-op.

`persistence_state` is provenance only, and the release watermark has no field
in the run document at all — `finalized_through` is derived from the ledger, so
a run cannot overclaim it. `max(last_seen)` is still not a watermark.

### Intent is declared, and a declaration the bytes contradict is refused

`kind` and `acquisition_id` are stated by the run, and the schema's
`if/then` pair makes the two halves unable to disagree. That is the 2B.2B rule.

This package takes it one step in the **reachable** direction. A `date_product`
whose body is exactly some acquisition's sealed artifact **for that date** is
rejected (`product_is_a_sealed_artifact`). The failure it catches is a producer
that omits `acquisition_id` on a real artifact: without the check the object
publishes as one the ledger makes no claim about, silently dropping the
checksum cross-check — the 2B.2B CLI defect arriving from the other side.
Verified reachable by mutation: disabling the check leaves exactly that test
failing and the other 34 passing.

## 2. Two jobs, because there are two authorities

`.github/workflows/v2_operational_publish.yml`:

| Job | Lane | Identity | Does |
| --- | --- | --- | --- |
| `stage` | 2, `araripe-green-candidate` | `v2-staging` | reads the run prefix, runs the ledger gate and the whole `check_green_release` chain, **writes nothing** |
| `promote` | 3, `araripe-green-promotion` | `v2-promotion` | publishes, verifies, then one pointer compare-and-swap |

The split is not two phases of one thing; it is the boundary the two
identities exist for. `PROMOTION_IDENTITY_SETUP.md`: *"if the two lanes used
the same key, any candidate run could move the pointer."* `needs: stage` makes
it operative — a malformed run fails under the **smaller** authority and the
larger one never starts.

**A test forced this design and it was right to.**
`test_the_candidate_identity_is_not_read_by_the_cli` pins from the file that
`publish_green_release.py` may not even *name* `R2_STAGING_*`. So the lane-2
half could not be a mode of that script, and `scripts/stage_green_run.py` is
its mirror image: it reads `R2_STAGING_*`, never names `R2_PROMOTION_*`, and
is handed a `ReadOnlyStore` whose three write methods raise. Both directions
are now asserted, and `test_the_read_only_store_overrides_every_write_the_base_class_has`
fails if a write is added to `ConditionalStore` later and not overridden.

### No pull request is expressible, which is the package

The property had to be structural rather than a policy, and it is read from
the file: `permissions: contents: read`, no job widening it, and no `git
commit`, `git push`, `gh pr create` or `GITHUB_TOKEN` anywhere in what the
shell executes. `test_the_blue_lane_publishes_through_a_pull_request_and_this_one_does_not`
reads *both* workflows, because the contrast is the point: `detect_gee.yml`
needs `pull-requests: write` and this file does not have it.

## 3. The promotion Environment: measured twice, and the answer changed

The briefing said `v2-promotion` might be created in parallel and to **measure,
not assume**. Measured at the start of the session:
`["cloudflare-green-control", "v2-staging"]` — absent. The lane was therefore
built complete and inert, naming the missing capability.

Measured again later in the same session:
`["cloudflare-green-control", "v2-promotion", "v2-staging"]`. The owner created
it while this package was being written, so the briefing's *"if it exists"*
branch applies and the job was bound to it. Read back before binding, without
touching a value:

    rules                    : ["branch_policy"]      (no required_reviewers)
    deployment branch policy : ["branch: main"]
    secrets                  : R2_PROMOTION_ACCESS_KEY_ID,
                               R2_PROMOTION_SECRET_ACCESS_KEY
    variables                : R2_STAGING_BUCKET, R2_ENDPOINT_URL, AWS_REGION

Exactly what `PROMOTION_IDENTITY_SETUP.md` specifies. No secret value was
requested, printed, copied or stored; secret values are not readable through
the API by design.

**A trap worth recording: never name an Environment that does not exist.**
GitHub does not fail on an unknown environment name — it creates one: *"Running
a workflow that references an environment that does not exist will create an
environment with the referenced name … the newly created environment will not
have any protection rules or secrets configured"*
(<https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments>).
A typo would therefore manufacture an unprotected environment with **no branch
policy at all** — an agent making a repository configuration change, and the
wrong one. This is why the inert version deliberately declared none rather
than declaring the name early.

## 4. A measured correction about the blue dependency pin

The 2B.2B decision to use the runner's Python plus `pip` rather than
`environment.yml` was recorded as decoupling. **It is stronger than that: the
blue pin cannot express the pointer compare-and-swap at all.**

`environment.yml` pins `botocore>=1.35.0,<1.36.0`. Unpacking the wheels and
reading `PutObjectRequest` in the S3 service model:

| botocore | `IfNoneMatch` | `IfMatch` |
| --- | --- | --- |
| 1.35.0 | absent | absent |
| 1.35.16 | **present** | absent |
| 1.35.36 | **present** | absent |
| 1.36.0 | present | present |

So the blue range resolves into a window where immutable write-once works and
`put_if_match` cannot be expressed — the worst shape, because publication would
succeed and only promotion would fail. `require_conditional_write_support`
checks **both** parameters against the loaded service model before any object
is touched, so that window fails closed rather than half-way through a release.
Its branch is not theoretical: this repository pins a range inside it.

The lane's pip floor is `botocore>=1.36.0`, **measured** rather than minimal —
versions between 1.35.36 and 1.36.0 were not tested, so 1.36.0 is the earliest
*measured* to carry both, not proven to be the earliest that does. The
environment this suite runs in is botocore 1.42.42 / boto3 1.42.44.

This is a note about the green lane only. **`environment.yml` is not modified
by this package** and no blue workflow is touched; the blue lane does not
import the publication code.

## 5. Lane distinctness, re-established over job-level groups

This is the first workflow whose jobs sit in two lanes, so it declares
`concurrency` per job and none at the file level.
`tests/test_workflow_lanes.py` reads only the workflow level — complete while
every file declared one group for the whole of itself — so this file would
have slipped through its sweep entirely.

The sweep is re-established in `tests/test_operational_publish_lane.py` over
both levels: every declared group across every workflow, blue members exactly
`detect_gee.yml` and `update_data.yml`, no green group equal to the blue one,
`cancel-in-progress: false` everywhere, and no green lane carrying a schedule.

`test_workflow_lanes.py` was deliberately **not** edited, for a reason outside
the design: another session was working in this same clone at the same time and
had that file modified. Rewriting it would have mixed two changes. The sweep is
equally strong in the new file and does not depend on the old one.

A group **may** have more than one member. `v2_promotion_lane.yml` and this
`promote` job both move the same pointer, so sharing
`araripe-green-promotion` is what serializes them — the same argument that puts
both blue state writers in one group. What must never happen is one group in
two lanes.

**Queue semantics, recorded rather than defended against.** Lane 3 holds one
running plus one pending run and drops a third. A `promote` dropped while
pending leaves its release fully written under its immutable prefix and the
pointer still on the previous, complete release. Re-dispatching the same run id
republishes byte-identically, because identity is a function of the ledger.

## 6. What was deliberately not built

- **No cron.** The roadmap bullet is "without PRs or manual merges", and what
  this removes from the data path is the pull request and the merge. A green
  lane carrying a schedule would break Package 2B.0 inertness (pinned by
  `test_green_lanes_cannot_inherit_a_schedule`), and there is no producer
  emitting runs on a schedule yet, so a cron would fire twice a week onto an
  empty prefix. Turning a cadence on belongs with turning the blue bot off,
  which is Phase 6.
- **No unreachable watermark check**, no second copy of anything
  `check_green_release` already establishes, and no `plan`-from-a-run mode
  duplicating `stage`.
- **No change to `data/timeseries/RELEASE.json`.** It stays blue, per briefing
  §4, and no evidence against that appeared: `site/scripts/check_backend_release.py`
  still accepts only `araripe.timeseries.release/1`. The green release is built
  beside it and the two meet at the Phase 6 cutover.

## 9. What the P2B exit gate still needs

The gate reads: *a deliberately failed or racing green run cannot corrupt blue
or expose a partial release; a staged test release can move and roll back its
green pointer without a manual data PR or any production effect.*

**Closed by this package:**

- *without a manual data PR* — the half 2B.2B left open. The operational path
  now reads from R2 and writes to R2, and the absence of a pull request is a
  property of the workflow file rather than a promise: no `contents: write`, no
  PR token, no git command.

**Still open:**

- **Everything is still proven against a fake store, not against R2.** The
  branch policy on both Environments admits only `main`, so nothing on a
  feature branch can reach a credential. The real-object proof needs the merge
  first — and `ci/promotion-identity-probe` exists precisely to be that proof.
- **No producer deposits a run prefix yet.** The lane consumes
  `runs/<run-id>/`; the 2A.6 producer that would write one is not on `main`.
  Until then a run prefix is uploaded deliberately. This is the same gap as
  "integration with a real 2A.6 producer run", which the roadmap already makes
  a gate condition.
- **Package 2B.3** — private/public R2 boundary, least-privilege credentials,
  the staged `/data/...` route, retention and deletion policy.
- **Package 2B.4** — green site artifact and deployment.
- **The Package 2B.0 lane proof** — four concurrent runs, four recorded URLs.
  Still a 2B.0 gate item, not this package's.

## 10. Live outside this package

`urs.earthdata.nasa.gov` has been unreachable from the runners since
2026-09-01, the site's rainfall has not updated since the 2026-08-25 raster,
and the **Friday 2026-09-11 run goes red** if it does not return.

**Setting `EARTHDATA_TOKEN` alone does not fix it**, and the earlier records
that said it did were incomplete. Verified by reading the site repository's
`origin/main` during this session: the `chuva` step of `update-data.yml` passes
only `EARTHDATA_USERNAME` and `EARTHDATA_PASSWORD` (lines 125-126), while
`scripts/fetch_gpm.py:98` and `scripts/earthdata_login.py:178` read
`EARTHDATA_TOKEN` — a name that never reached the script, so defining the
secret had no effect at all. The same dead-secret shape as the backend's
`EE_PROJECT`.

The fix is `observatorio-site#18`, **open and needing explicit human approval**
because `update-data.yml` is a blue workflow. So the owner's action is two
things, not one: approve that PR *and* set the token. Neither is part of
Package 2B.2.
