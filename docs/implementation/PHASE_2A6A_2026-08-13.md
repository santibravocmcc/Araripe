## Acquisition and observation identity

`src/detection/identity_v2.py` implements a physical acquisition as the unique
grouping key `platform + datatake_id + acquisition_timestamp_utc`. A run
manifest cannot contain that physical key twice, even if two records claim
different scene sets. Acquisition identity additionally binds collection,
UTF-8-sorted native scene IDs, monitoring extent, selected composition-method
ID, and grid ID. Run-manifest identity is carried and validated on the document
but deliberately excluded from the acquisition ID so an unchanged physical
datatake retains its ID in a reviewed rebuild.

UTC timestamps are canonicalized to explicit `Z` form. Acquisition and ledger
order parses the instant and then uses `acquisition_id` as the deterministic
tie-break; it does not use unsafe lexical timestamp ordering when fractional
seconds are present.

Observation identity binds the v2 acquisition ID, canonical geometry SHA-256,
algorithm version, and baseline version. The raw observation contains no
mutable event or persistence assignment. Standalone validation rederives the
identity and canonical geometry, and exported observation dictionaries are
deep copies so callers cannot mutate the source record through an exported
nested object.

## Manifest-bound processing ledger

`src/detection/ledger_v2.py` accounts for expected physical acquisitions, not
dates. It binds the complete expected acquisition set to the run-manifest ID
and checksum and orders records by acquisition timestamp/ID. Ledger identity
also seals the monitoring extent, algorithm version, and canonical expected
acquisition set, so those scientific bindings cannot drift behind the same
ledger ID. Each expected acquisition accepts exactly one of seven terminal
statuses:

- `complete_with_alerts`;
- `complete_zero_alerts`;
- `rejected_low_coverage`;
- `rejected_quality`;
- `failed_download`;
- `failed_missing_input`; or
- `failed_processing`.

An exact terminal-row retry is a byte-preserving no-op; a conflicting row fails
closed. A daily summary and serializable ledger exist only after every expected
acquisition for every represented UTC date is terminal. The semantic validator
reconstructs the complete ledger and rejects altered row, summary, document,
identity, count, order, or reconciliation hashes even when an attacker has
recomputed enclosing checksums. Persistence finalization is rejected when its
transition timestamp precedes the latest terminal-row timestamp expected for
that date.

The finalized-date input digest binds the expected acquisition set, statuses,
observation IDs, artifact checksums, stable reason codes, and a checksum of the
stable scientific projection of every complete observation record. The
projection excludes only operational `run_manifest_id`,
`run_manifest_sha256`, and `created_at`; geometry, area, acquisition timestamp,
extent, versions, policies, and identities remain bound. Consequently, an
overlapping rolling-manifest retry with identical science remains a no-op,
while changed scientific bytes under a reused observation ID fail closed and
require a new chronological generation.

## Atomic daily persistence and lineage

`src/detection/persistence_v2.py` applies a terminal UTC date atomically in two
phases. It first reconciles every observation to the manifest ledger and then
processes acquisitions in timestamp/ID order and observations in observation-ID
order. Only after the whole date succeeds does it materialize contributions,
finalized-date evidence, the watermark, and a sealed state.

All same-day datatake observations remain independent. An event receives at
most one `pc-v2-*` contribution for that UTC date, aggregating sorted unique
source acquisition and observation IDs, and only after all manifest-expected
acquisitions for the date are terminal. Zero-alert and rejected/failed terminal
dates still close the date and advance the watermark without inventing a
contribution.

An exact finalized-date replay returns the original state bytes and historical
assignment counts/tiers. A different input digest for a finalized date raises
`LateArrivalRequiresRebuild`; an older unfinalized date raises
`OutOfOrderRequiresRebuild`. `rebuild_persistence_state_v2` starts a new
`gen-v2-*` state from empty and replays every terminal date canonically. It
rejects observations outside the ledger rather than silently ignoring them.

Origin, continuation, split, and merge identities and lineage are deterministic.
Raw observation IDs stay preserved when parent events become superseded. State
validation rederives event, lineage, and contribution identities and geometry
hashes; fixes confirmation at 15 distinct contributed dates, reconnection at
180 days, and minimum overlap at `0.05`; reconciles event dates, tiers,
acquisition/observation sources, finalized-date lists, current manifest
binding, and watermark; and requires exact bidirectional lineage references.
Continuation is a self-edge, while split and merge children and their triggers
must exactly match their event identity bases and effective contributions. An
origin observation must belong to the origin event's first-date contribution,
and representative geometry must derive an observation ID already carried by
the event. One observation cannot be assigned to multiple event contributions.

State identity seals generation, manifest, extent, algorithm, baseline, fixed
transition policy, finalized dates, events, lineage, contributions, and
watermark. Event/lineage/contribution IDs are unique, event status and the last
transition are derived from state contents, and all persisted timestamps use
one byte-canonical UTC representation.

## Executable v1 audit-only boundary

V2 has its own runtime modules and serializer. The generic v2 boundary validates
both JSON Schema and contract semantics before reading or emitting bytes.

Legacy v1 identity helpers now require exact v1 prefixes and lowercase
SHA-256-shaped IDs before deriving observation, event, lineage, or contribution
identities. V1 acquisition metadata, scene-quality, persistence-state, and
time-series database writers reject v2 types or prefixes before writing. This
prevents a v2 acquisition or derived record from being silently relabelled and
serialized through an audit-only v1 path while preserving valid v1 round trips.

## Independent adversarial review

An independent read-only runtime review was performed after the first green
test run. That first result was explicitly discarded when the review found
semantic gaps not exercised by the initial scenarios. The final implementation
and regressions close all reported blockers:

- duplicate physical acquisition keys;
- JSON-Schema-only ledger serialization;
- changed scientific observation bytes hidden behind the same ID;
- configurable confirmation thresholds diverging from the state contract;
- state tier, identity, geometry, and reciprocity tampering after outer reseal;
- invalid reason tokens accepted before schema serialization;
- lexical fractional-timestamp ordering;
- non-historical assignment values on an old-date replay;
- incomplete v1 persistence-writer isolation;
- mutable state policy and incomplete ledger/state identity bindings;
- duplicate state IDs, ungrounded status, and inconsistent last-transition
  metadata;
- finalization timestamped before all expected terminal rows;
- lineage rewiring, child/trigger mismatch, and non-self continuation;
- representative event geometry disconnected from raw observations;
- alternate non-canonical timestamp byte forms; and
- origin-event re-keying to an observation from a later date.

The review found no implementation of Packages 2A.6B--2A.6D and no production
or Package 2B.0 mutation.

This package does not implement or activate `scl-explicit-allowlist-v2`,
datatake-scoped coverage-ranked composition, local/GEE parity, baseline rebuild,
2026 candidate replay, or MapBiomas Collection 10.1 export. It does not wire the
new contracts into the legacy date-collapsing entrypoints. Those changes belong
to Packages 2A.6B--2A.6D and must consume, not redefine, this v2 family.

Package 2A.6A is technically complete. The broader Package 2A.6 and exit gate
P2A remain open pending Packages 2A.6B--2A.6D and their targeted gates. No
qualified scientific-accuracy or publication claim is made.
