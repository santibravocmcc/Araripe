## Rebuild machinery (src/processing/baseline_rebuild_v2.py)

The module consumes — never redefines — the closed science and contracts:
`scl_mask_v2` (mask and fail-closed metadata gates), `composition_v2`
(datatake-scoped composition), `gee_composition_v2` (explicit plan, local
mosaic-semantics execution, byte parity), and `identity_v3` (acquisitions).

- **Reviewed-baseline registry.** The closed
  `araripe-reviewed-processing-baselines-v1 = {05.11, 05.12}` is the base
  enumeration. Historical baseline-source years are expected to surface
  other provider baselines; `load_baseline_rebuild_registry` accepts them
  only through a recorded-review extension document (reviewer, ISO date,
  scope, and per-value review basis and observation source, values already
  in normalized NN.NN form, no duplicates, no base overlap). Without a valid
  extension the consumed modules keep failing closed
  (`UnreviewedProcessingBaselineError`); extension is an explicit argument,
  never a fallback. Every observed value is enumerated in month evidence and
  the manifest.
- **Declared source datatakes.** `declare_baseline_source_datatake` accepts
  only the accepted source years {2017, 2019, 2021, 2022, 2025}, requires
  the acquisition timestamp to sit inside its declared year/month slot and
  to equal the sensing instant embedded in a provider `GS2*` datatake
  identifier, requires the exact five-band contract (B11, B12, B4, B8, B8A),
  and requires the scenes to form exactly one physical datatake.
- **v3 identities and the platform gate.** Each source datatake binds an
  `acq-v3-` acquisition through `create_acquisition_v3`; the v3 contract —
  not this module — decides platform representability, so Sentinel-2C
  composes end to end while Sentinel-2D fails closed before any pixel is
  read. `V3_REPRESENTABLE_PLATFORMS` is proven against the contract by
  test, not asserted independently. Replay-facing identity work stays on
  the v3 family; nothing serializes into v1/v2 (audit-only) schemas.
- **Counts-derived GEE plan.** `build_rebuild_gee_plan` emits the exact
  2A.6B `gee-coverage-ranked-first-valid-plan-v1` structure from explicit
  per-scene valid-pixel counts (`derive_first_valid_order`; count source
  recorded as `local_reference_composite` or `gee_reduce_region`), so the
  production-scale executor derives the identical plan from GEE
  `reduceRegion` counts with no local pixels. Fixture-scale tests prove the
  counts-derived plan passes `execute_gee_plan_locally` and byte-identical
  `assert_local_gee_parity` against the composed reference, that tampered
  order or wrong counts fail the parity gate, and that
  `compose_rebuild_datatake` embeds this plan-plus-parity path for every
  successful composite.
- **Indices and monthly statistics.** Indices (`evi2`, `nbr`, `ndmi`; the
  v1 formulas on reflectance) are computed on composed bands only — every
  band of a pixel from one scene — with non-finite results counted and
  excluded as missing. `compute_monthly_baseline_statistics` stacks each
  month's datatake composites in canonical chronological order and produces
  the multi-year monthly median, the population standard deviation
  (`ddof=0`, matching the v1 GEE `stdDev` reducer), and a contribution-count
  grid; float64 computation, float32 output, permutation-invariant to the
  byte, with a checksummed month-evidence document enumerating datatakes,
  scenes, baselines, platforms, plan/parity checksums, and array digests.
- **Deterministic rebuild plan.** `build_baseline_rebuild_plan` fixes the
  whole instruction sheet (collection, years, months, scene admission
  carried unchanged from the accepted 1.0.0 configuration, extent, audited
  grid, mask, composition, GEE two-phase execution rules, platform policy,
  statistics, output contract, and the v1-immutability pins) under a
  canonical checksum; `run_manifest_binding_from_plan` derives the v3
  run-manifest binding from that checksum, so identical plans always bind
  identical acquisition documents.

## Baseline 2.0.0 manifest discipline (src/detection/baseline_manifest_v2.py)

- **Package 2A.2 discipline retained.** The rebuilt directory is audited by
  the same authoritative reader as the 1.0.0 audit (`expected_filenames`,
  full-raster checksums, grid, scale, range limits per index/statistic,
  wider-extent coverage ≥ 0.99), then held to the pinned 2.0.0 grid
  contract — the audited 1.0.0 grid, unchanged, for pixel compatibility.
- **Execution-time provenance now mandatory.** The 2A.2 audit's "missing"
  list is the v2 "retained" contract: per-datatake scene IDs, per-scene
  processing baselines, per-scene valid-pixel counts, GEE project and task
  IDs, query fingerprint, month-export checksums, per-datatake plan
  checksums, and statistics evidence. `provenance_completeness.missing`
  must be empty.
- **Re-derived identities.** `validate_manifest_v2` never trusts
  identity-bearing fields: every `acquisition_id` is recomputed through the
  v3 contract (which also fails closed on any platform beyond S2A/S2B/S2C)
  and every per-datatake `gee_plan_sha256` is recomputed from the entry's
  own scene counts. The run-manifest binding must equal the rebuild plan
  checksum. Mask, composition, and statistics blocks must equal the runtime
  policy constants exactly — the mask-baseline identity gate that makes a
  v1-mask manifest unrepresentable as 2.0.0.
- **Baseline 1.0.0 immutability.** The v1 manifest bytes are pinned
  (`15a1ed3cea7c804d18d2c82c86a7b9a030687fedb01b315d543965b1f26f0a82`) and
  `require_baseline_v1_untouched` verifies both the pin and the v1
  validator. v2 object keys live under the disjoint prefix
  `baselines_v2/2.0.0/` (never under the v1 `baselines/` listing prefix),
  the local directory is `data/baselines_v2/2.0.0`, and `write_manifest_v2`
  refuses the v1 manifest path and any existing file. A stored manifest is
  validated against the pinned production contract — its embedded contract
  cannot vouch for itself.
- **Decision bindings.** The manifest pins the 2026-08-11 decision record
  and the Sentinel-2C v3 amendment by SHA-256, the immutable predecessor
  block, and the accepted wider monitoring extent unchanged.

`scripts/rebuild_baseline_v2_manifest.py` is the executor-facing CLI: it
verifies 1.0.0 untouched, audits the rebuilt directory, joins the execution

## Addendum 2026-09-05 — execution-path hardening before the Earth Engine run

The owner activated the Earth Engine capability (approved project
`ee-araripe-baseline-v2`, project number `344946877764`, local interactive
authentication, `earthengine-api` 1.7.42 in the `araripe` environment) and
directed that version artifacts must not mix under any circumstance, and that
the remaining execution-shape choices be made under best practice and
scientific rigour. This addendum records what changed before execution; the
2026-09-01 sections above are unchanged history.

### Physical version isolation

Isolation is now enforced by code rather than by convention. A 2.0.0 rebuild
and the immutable 1.0.0 generation share no Drive folder
(`araripe_baselines_v2`), no export filename (`araripe_baseline_v2_monthNN`),
no object-key prefix (`baselines_v2/2.0.0/`), no local directory
(`data/baselines_v2/...`), no manifest path, and no splitter. The manifest
validator rejects a v1 export name, a v1 Drive folder, and a v1 prefix; the
new splitter refuses to write anywhere inside `data/baselines/`, and refuses
any input file that is not a canonical v2 monthly export name.

### Contribution depth is now recorded evidence

Detection divides an observation's departure by this baseline's monthly
dispersion. Under the accepted datatake-scoped method, the monthly statistics
reduce over *datatake composites*, so a pixel may rest on very few of them;
with one composite the population standard deviation is exactly zero and with
two it is arithmetically defined but statistically meaningless. The 1.0.0
generation could not express this at all, and a silently shallow pixel
manufactures false alerts.

Each monthly export therefore carries nine bands — the six statistics plus a
per-index contribution count. The counts are split into rasters held
**outside** the audited directory (which must contain exactly the canonical
72), checksummed, and summarised in the manifest as minimum, maximum, median,
the zero tail, and the below-three tail per index and month.

No minimum-depth threshold is imposed. Choosing one is a scientific decision
that requires the depth distribution first and belongs to the owner and Phase
5; the rebuild measures and reports, and the manifest states that explicitly.

Validation gained a cross-check that binds the two sides together: a monthly
statistic is finite exactly where at least one composite contributed, so each
audited raster's finite-pixel count must equal the grid size minus that
index/month's zero tail. Fabricated coverage on either side fails.

### Fail-closed range handling in the split

The v1 splitter masks any `|value| > 1.5`, which is looser than the v2 range
contract for NDMI and NBR (`[-1, 1]`). Inheriting that would let a genuine
anomaly be masked away into a manifest that then validates. The v2 splitter
clamps only within a `1e-6` numerical tolerance, counts what it clamped, and
otherwise **fails closed** with a diagnostic naming the index, month, pixel
count, and observed extremes.

### Reproducible query identity

`baseline_query_fingerprint()` canonically hashes the exact source selection
(collection, years, months, cloud filter, extent, grid, bands, reflectance
divisor). The 2A.2 audit recorded that the historical query fingerprint was
irrecoverable; the v2 manifest now carries one that a future generation can be
compared against rather than merely described.
