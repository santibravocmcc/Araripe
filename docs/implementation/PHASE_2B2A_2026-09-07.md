**Started:** 2026-09-07
**Base:** `origin/main` at `ff4eea6e6358e2561a4823caa701a41235d91029`
**Branch:** `claude/phase2b2a-ledger-binding` (backend only)
**Production impact:** none. No R2 read or write, no workflow dispatch, no

Package 2B.2 is estimated at 50k–80k, "Very High" — roughly double 2B.1 — so it
is sliced, as Package 2A.6 was. This is the first slice: **bind the contract and
consume the ledger**. Publication is 2B.2B and is not started.

## 1. The binding: the v3 family, at `3.0.0`

The decision was already taken by the owner and is not reopened here. What this
package adds is that the decision is now *recorded where the code reads it* and
*enforced*, rather than living in a prompt:
`docs/contracts/phase2b/LEDGER_CONTRACT_BINDING_V1.md` holds the rationale and
[`ledger_contract_pin.json`](../contracts/phase2b/ledger_contract_pin.json)
holds the machine-readable pin that `src/publication/ledger_binding.py` verifies
before any ledger is looked at.

The roadmap bullet says "v2". That wording **predates the 2026-09-01
Sentinel-2C amendment**, and the binding document says so and says why: 20 of
the 70 retained Phase 2A.4 pilot scenes are `GS2C_*`, the v2 `platform` enum is
`S2A`/`S2B`, an enum change is major under the Phase 1 compatibility policy, and
so the v2 family stands closed at `2.0.0` with no `S2C -> S2A` relabelling
anywhere. Binding publication to v2 would leave it structurally unable to
account for 20/70 of the pilot's acquisitions.

Two tests hold the decision to its reason rather than to its wording:
`test_a_sentinel_2c_acquisition_is_representable` requires the pinned
acceptance fixture to contain an `S2C` acquisition *and* to pass the gate, and
`test_a_v2_ledger_is_refused_rather_than_coerced` requires a `2.0.0` document to
be rejected with `contract_binding_mismatch` rather than read as if it were v3.

No evidence against the v3 choice appeared while implementing it.

## 2. The pin, and what "fail closed on a silent producer change" means

`main` had no `docs/contracts/` at all: the entire contract tree lives only on
`claude/phase2a6d-mapbiomas` (`64fd781f1551a45914a7db32960b923c05056955`). Four
artifacts are now copied onto `main` **byte-identically, at the producer's own
paths** — the ledger schema, the producer's ledger example, and both contract
documents — with their SHA-256 and byte length pinned.

Copying to the producer's paths rather than a `phase2b/` mirror is the
load-bearing choice. There is then exactly one copy of the schema in the
repository (`test_the_ledger_schema_is_vendored_only_at_the_producers_own_path`),
`src/detection/contracts_v3.py` already resolves schemas from that directory so
producer and consumer will read the same file once 2A.6 lands, and a later 2A.6
merge that changes the ledger contract lands on these exact paths — where it
either leaves the bytes identical or breaks the pin and stops the gate.

Four separate properties make drift fail closed, and only some can run
everywhere. Conflating them would be the same class of error this package
exists to prevent, so they are distinct in code and in the document:

| Property | Catches | Available |
| --- | --- | --- |
| Pinned-byte integrity | an edited vendored artifact; a 2A.6 merge that changes the contract | always |
| Document binding | a producer emitting a different major | always, at run time |
| Producer-blob agreement at the pinned **commit** | a pin that was typed rather than taken | only where that commit is in the clone |
| Ref drift at the producer **branch** | the producer moving away from what we consume | only where that ref is in the clone |

The third exists for a specific reason: on 2026-09-07 a commit message asserted
a "verified base" carrying a 40-character SHA whose last 33 characters were
invented from the 7 that were known, and review did not catch it because a
plausible identifier reads like a checked one. The pin is now machine-compared
against the producer's own bytes. Where a revision is absent from the clone
these two checks report `unverifiable` and say so; they never report success
they did not establish.

**Nothing about the ledger's shape is copied into code or into the pin.** The
`schema_version` constant, the seven-value terminal status vocabulary and the
four ID patterns are all read back out of the pinned schema, so the schema stays
the single source of truth and its digest protects all of it at once. The pin's
declared version is cross-checked against the schema's own constant, so a pin
that disagrees with its bytes fails closed
(`test_a_pin_that_disagrees_with_its_schema_is_refused`).

## 3. Recomputing the producer's digests without importing the producer

The ledger is self-describing: it carries digests for its expected set, its
rows, its summaries, each individual row, each summary, and the whole document.
A consumer that cannot recompute them can only *believe* them.

The producer hashes with `src.detection.identity.canonical_sha256`, which is not
on `main` and cannot be brought here without `identity_v3`, `persistence_v3` and
their Shapely geometry primitives. So `src/publication/canonical_json.py` ports
exactly one property: the producer's `jcs_dumps` for the value types a ledger
actually contains — strings, integers, booleans, null, arrays, objects. Anything
it cannot reproduce byte-for-byte it **refuses**: floats (RFC 8785 §3.2.2.3
number formatting is the one part of JCS with real implementation risk, and the
ledger has no floating-point field), non-string object keys, lone surrogates,
and integers outside the JCS interoperable range. It therefore either agrees
with the producer or raises; it has no silent-disagreement path.

Agreement is executed, not asserted.
`test_every_digest_the_producer_embedded_recomputes_here` recomputes all six
document-level and collection-level digests plus every per-row and per-summary
digest in the producer's committed fixture and requires equality;
`test_the_producers_identity_formulas_recompute_here` does the same for both
acquisition identities and the ledger identity. Key order is UTF-16BE code
units, and `test_keys_are_ordered_by_utf16_code_unit_not_code_point` pins the
one case where that differs from Python's `sort_keys`.

## 4. One terminal row per expected acquisition, and a summary that reconciles

`src/publication/ledger_gate.py` is Topic 31 on the consumer side.
`scripts/check_processing_ledger.py` is the operator entry point
(`--binding`, `--self-test`, or a path).

`ProcessingLedgerV3._document_unvalidated` already refuses to serialize an
incomplete ledger, so a document that came from that producer unmodified always
passes. **That is the point.** The gate exists for the documents that did not: a
truncated or partially written object, a hand-assembled or replayed ledger, one
from a different run manifest, or one from a later producer. Topic 31's
"incomplete runs never replace the last complete release" is only enforceable if
the publication side can tell those apart without trusting the document's own
`integrity` block — which is why every digest in that block is recomputed rather
than read.

Rejections are **collected, never raised on the first one**. Package 2B.1's
state validator died on the first bad feature and the log could not distinguish
one odd row from a hundred thousand; here each finding carries a stable code and
the JSON path it applies to, and the message leads with the count and a
code histogram (`test_the_rejection_message_summarizes_before_it_enumerates`).

### Where the schema stops and the gate starts

The pinned schema owns *shape*: field presence, types, the status enum, the
per-status output/reason combinations, and the `terminal` /
`persistence_finalization_allowed` / `integrity` constants. The gate owns only
what JSON Schema cannot express — comparing one array against another,
recomputing a digest, checking chronological order, relating counts to array
lengths, and relating rows to the manifest-bound expected set.

This division was reached by deleting code. A first version of the gate also
re-checked the status enum, the per-status output/reason rules and the three
boolean constants. Because both layers read the *same* pinned schema file, those
branches were unreachable — not defence in depth, but code that looks like
protection and can never fire. They were removed.

One consequence is worth stating plainly, because the briefing asked for a
deterministic test for a "non-terminal row": a status outside the seven-value
vocabulary is refused at the **schema** layer, and
`test_a_non_terminal_status_is_refused_by_the_pinned_contract` asserts exactly
that, including that the message names both the offending status and the
permitted ones. The gate keeps no second copy of that list to check against. The
non-terminal cases the gate itself owns are the ones the schema cannot see: an
expected acquisition with no row at all, a date whose summary claims terminality
while a row is missing, and a `terminal_at` that precedes its acquisition.

### Only producer-promised properties are asserted

Every rule maps to the line of `src/detection/ledger_v3.py` or
`identity_v3.py` that guarantees it; the table is in
`LEDGER_CONTRACT_BINDING_V1.md` §4. Three properties are **deliberately not**
required, and each is recorded with its reason in §5 of that document:

1. **Canonical bytes on disk.** `serialize_v3_document` writes canonical bytes
   plus a newline, but `generate_v3_examples.py` writes
   `json.dumps(..., indent=2)`. The producer's own committed fixture is
   pretty-printed, so a gate requiring canonical *file* bytes would reject it.
   This was caught by measurement, not by reading: the first probe of the
   canonicalization compared file bytes and failed on that one check while all
   eight digest checks passed. It is now pinned as a negative result in
   `test_the_gate_verifies_digests_rather_than_file_bytes`.
2. **A null `artifact_sha256` on rejection and failure rows.** The producer
   requires a checksum for the two success statuses only; for the five
   rejection/failure statuses the field is unconstrained.
3. **A uniform `collection_id`, `composite_method_id` or `grid_id` across the
   expected set.** `ProcessingLedgerV3.__init__` checks the manifest binding and
   the monitoring extent, and deliberately not these. Requiring uniformity would
   fail closed on a mixed-method manifest the contract permits.

That discipline is the 2026-09-07 lesson applied: a fail-closed check may only
require what the producer actually promises, or the safeguard becomes the
outage.

### The chronological trap, verified rather than trusted

`acquisition_order_key` parses timestamps instead of comparing strings because
`.` sorts before `Z`, so a fractional-second timestamp sorts *earlier*
lexically and *later* chronologically than a whole-second one in the same
second. `test_chronological_order_is_by_instant_not_by_string` builds exactly
that pair — `13:12:41Z` and `13:12:41.5Z` — asserts the fixture is one where the
two orders disagree, and requires the correctly ordered ledger to be
**accepted**. A string comparison would reject it.

### `jsonschema` in `environment.yml`, and its measured cost

Validating against the 2A.6 schema needs `jsonschema`, which the science branch
declares and `main` did not. It is now declared with the science branch's exact
spec (`jsonschema>=4.23.0`) so the two files converge when 2A.6 merges.

Unlike 2B.1's `pyyaml`, this is **not** solve-neutral, and that was measured
rather than assumed. `conda env create --dry-run` on `main`'s `environment.yml`
before and after, on osx-arm64:

```
282 packages → 286 packages
+ conda-forge/noarch::jsonschema==4.26.0
+ conda-forge/noarch::jsonschema-specifications==2025.9.1
+ conda-forge/noarch::referencing==0.37.0
+ conda-forge/osx-arm64::rpds-py==2026.6.3
```

Nothing was removed and **no existing package changed version**. All four are
pure Python except `rpds-py`, which ships wheels/conda builds. The runners solve
linux-64, so the `rpds-py` build string will differ there; the shape of the
change should not.

`pinned_validator()` imports `jsonschema` lazily and raises
`ContractBindingError` naming the missing capability if it is absent, so an
environment without it makes the gate refuse rather than silently skip
validation.

## 7. What the P2B exit gate still needs

The gate reads: *a deliberately failed or racing green run cannot corrupt blue
or expose a partial release; a staged test release can move and roll back its
green pointer without a manual data PR or any production effect.*

Package 2B.2A contributes the part of the roadmap's Package 2B.2 that the gate
names as a precondition rather than a clause: *"the P2B gate cannot close before
integration with the 2A.6 producer passes."* That integration now exists as a
pinned, executable contract boundary with 69 tests. It does **not** close the
gate, and it does not touch the "partial release" clause. Still open:

- **Package 2B.2B — the "cannot expose a partial release" clause itself.**
  Immutable release/staging identity, validation before green pointer
  promotion, conditional writes so an older or racing job cannot replace a
  newer release, keeping the last complete release live on partial failure, and
  explicit zero-alert dates and stale-object tombstones. None of it is started.
- **Package 2B.2C** — taking operational publication off the git pull-request
  lane. Where a ledger is published is unresolved; publishing at a new git path
  would need the `detect_gee.yml` publish guard changed, which is a blue
  workflow and needs approval, so the roadmap's "automatic without PRs" points
  at R2.
- **Package 2B.3** — private/public R2 boundary, least-privilege credentials,
  staged `/data/...` route against the isolated staging Worker.
- **Package 2B.4** — green site artifact and deployment, automatic publication
  without bot pushes, pinned actions and locked environments.
- **The pointer half of the gate** — moving and rolling back a green staging
  pointer still needs the 2B.2B publication contract; `v2_promotion_lane.yml`
  remains the 2B.0 placeholder.
- **The runnable lane proof from 2B.0** — four concurrent runs with four
  recorded URLs. This package adds nothing to it, but one blocking claim
  carried in the 2B.1 record is **stale and is corrected here**: that record
  says the proof "awaits the v2 workflows reaching the default branch through
  a reviewed merge". They reached it. `git ls-tree --name-only origin/main --
  .github/workflows/` lists both `v2_candidate_replay.yml` and
  `v2_promotion_lane.yml`, landed by squash `8daa181` ("Package 2B.0: isolated
  green broker and inert workflows (#10)"). What the proof actually needs now
  is the dispatch itself.

  Two measured constraints on that dispatch, for whoever runs it:
  `gh api repos/santibravocmcc/Araripe/environments/v2-staging` shows one
  protection rule of type `branch_policy` and **no reviewer**, and
  `.../deployment-branch-policies` allows exactly one branch, `main`. So
  `v2_candidate_replay.yml`, which declares `environment: v2-staging`, can only
  run from `main` — a green workflow on a feature branch cannot reach that
  Environment at all. `v2_promotion_lane.yml` declares no environment and no
  secret, so it is dispatchable from any ref. 2B.1's static half remains in
  `tests/test_workflow_lanes.py`.
